## D-01 为什么挂两个点：审批请求里没有命令文本（2026-11-01）

**现象**：想按命令正则自动同意审批，但 `approval/request` 的 `req` 只有
`{agent, toolName, callId, reason?, displayReason?, signal?}`——**没有命令原文**。只靠这个事件
只能按工具名放行（`toolName === 'pwsh'`），那等于把 pwsh 全放开。

**根因**：审批是「要不要问」的决策点，不是「执行什么」的决策点。命令文本在工具执行层，
不在审批层。官方 `dsh-experimental-auto-review` 同样是在 `tools/pre-execute` 拿
`exec.name` / `exec.arguments`，再在审批瀑布里给结论。

**结论**：

- `tools/pre-execute`（`{prepend:true}`）：只把 `exec.callId → {tool, command}` 记进有界缓存，
  然后原样 `next()`。**不在这里做放行判断**——pre-execute 的返回语义是 gate
  （`allow` / `ask` / `deny`），在那里直接 allow 会越过后续 guard，也会让「普通审批」和
  「提权审批」混在一起。
- `approval/request`（`{prepend:true}`）：用 `req.callId` 取缓存命令 → 查配置 →
  命中 allow 且未命中 deny 才返回 `'allowed-once'`，否则 `next()`。

**被否方案**：

| 方案 | 为什么否 |
| :--- | :--- |
| 在 `tools/pre-execute` 里匹配并 `return {kind:'allow'}` | 越过了该点之后的 guard / ask 语义；审批瀑布才是「问人」的唯一出口，两处做决定会打架 |
| 从 session 事件日志（`tool/call`）里按 callId 反查命令 | 依赖 DSH 内部日志格式与回放规则，慢且随版本变；pre-execute 是公开扩展点 |
| 只按 `toolName` 放行 pwsh/bash | 等于关掉这两个工具的审批，和需求相反 |

**复验**：`tests/allow.test.mjs` 的「缓存命中」「缓存未命中」「callId 缺失」「非 pwsh/bash」四组。

## D-02 强制全串锚定，且匹配必须覆盖整条命令（2026-11-01）

**现象**：如果允许 `match: "^git pull"` 这种前缀规则，`git pull; rm -rf ~` 会被自动同意。
命令里的 `;`、`&&`、换行都能把一条「安全命令」变成任意脚本。

**根因**：审批的对象是**整条命令字符串**。前缀/包含匹配把「命令开头像 X」当成「命令就是 X」，
两者之间没有任何语法保证。

**结论**：

- `match` 必须以 `^` 开头、以 `$` 结尾，否则**该条规则作废**（写诊断，不放行）；
- 编译后用 `exec` 校验 `match.index === 0 && match[0].length === command.length`。
  只查 `^`/`$` 不够：JS 的 `$` 允许匹配末尾换行之前的位置，`^git status$` 会匹配
  `"git status\n"`，长度校验把这个口子堵死；
- 正则不带 flag（区分大小写），`.`/`.*` 不跨行；多行命令要显式写 `[\s\S]*`。

**被否方案**：

| 方案 | 为什么否 |
| :--- | :--- |
| 前缀匹配 / `includes` | 上面的反例；无法判断命令边界 |
| 自动给用户写的 `match` 补 `^…$` | 掩盖配置错误；用户可能故意写 `^foo$|^bar$`，自动补会把语义改坏 |
| 只查字符串首尾是不是 `^`/`$`、不做长度校验 | 留 `"git status\n"` 的换行口子 |
| 拆复合命令后再逐段匹配 | 见 D-06：需要 shell 解析，MVP 不做 |

**复验**：锚定校验、`^git commit -m '.*'$` 匹配/不匹配、末行换行三组测试。

## D-03 deny 优先，全局与项目段都生效（2026-11-01）

**现象**：全局 allow 一条 `^git push .*$`、项目 deny 一条 `^git push .*--force.*$` 时，
如果按「先命中先赢」或按文件顺序，强推会被全局 allow 放过。

**根因**：allow 是油门，deny 是刹车。两条规则同时命中说明配置在这一点上自相矛盾，
矛盾时唯一安全的选择是「问人」。而且用户加 deny 的动机往往就是「这条就算 allow 命中也不许自动过」。

**结论**：先扫全部 deny（全局 ∪ 当前项目段），命中即 `next()`；再扫 allow。deny 的 `rule` 与
`reason: "deny-rule"` 写审计，方便统计「哪些规则在踩刹车」。

**被否方案**：项目段覆盖全局（项目 deny 只挡项目 allow）、后写覆盖先写、按规则数组顺序先命中先赢。

**复验**：`deny 优先` 与 `全局与项目段合并，项目 deny 优先` 两组测试。

## D-04 单条规则作废，结构错误按层级作废（2026-11-01）

**现象**：一份名单里有一两条正则写坏（少括号、忘锚定、拼错字段）时，不能让另外 20 条好规则
一起失效；但坏掉的部分绝不能因为「跳过」而被当成放行。

**根因**：配置错误和配置内容要分开处理。规则级错误是局部笔误；文件级错误是整份文件不可信
（坏 JSON、`version` 不对、顶层 `deny`/`allow` 不是数组、未知顶层字段）；`projects` 段是
可选的附属块，坏一块只该丢一块，不该连带把全局规则一起废掉。

**结论**：

- 文件级错误 → 该文件**整份不生效**（不贡献任何规则、也不贡献项目段），写一条诊断；
- `projects` 不是对象 → 只忽略 projects 段，顶层规则照常生效，写一条诊断；
- 单个项目项坏（键不是项目标识、值不是对象、未知字段、`deny`/`allow` 不是数组）→ 只丢该项，
  其它项目项与全局规则照常，写一条诊断；
- 规则级错误（非对象、缺 `id`、缺/空 `tool`、非锚定、坏正则、未知字段）→ **只丢这一条**，
  兄弟规则照常；项目段里的规则错误只影响该项目段里的那一条；每条错误写一条诊断；
- 所有情况都 fail-closed：被丢掉的部分永远不会放行；
- 诊断追加到 `<dataDir>/config-errors.log`，一行一条 JSON（`ts` / `source` / `file` /
  `ruleId` / `error`），同一文件同一 stamp 只报一次，避免每次审批刷日志；
- 顶层、`projects` 段与规则里 `_` 开头的键按注释忽略，方便在 JSON 里写说明。

**被否方案**：

| 方案 | 为什么否 |
| :--- | :--- |
| 任何错误都整份作废 | 一个拼写错误让整张名单失效，排查成本高，且用户会以为「插件坏了」 |
| 静默跳过坏规则 | 用户不知道规则没生效，以为放行了其实每次都在问 |
| 遇到坏配置就自动全放行 | 直接违背 fail-closed |
| 用宽松解析（`JSON5` / 容错库） | 多一个依赖；且容错会把「写错」变成「猜你想写什么」，不适合安全规则 |

**复验**：坏 JSON、坏正则、不锚定、未知字段、`version` 不是 1、`projects` 段异常六组测试。

## D-05 项目根取会话工作目录，只用来算项目标识（2026-11-01）

**现象**：项目段要按「当前会话在哪个项目」查，但宿主进程的 `process.cwd()` 是 DSH 启动目录，
和当前会话在哪个项目没有关系；用它会把 A 项目的规则套到 B 项目。

**根因**：DSH 的「项目」是会话状态，不是进程状态。`workingDirectory` 服务按 session 投影
保存已提交的工作目录，且 `get(session)` 不读磁盘。

**结论**：

- 一手来源：`ctx.get('workingDirectory')?.get(exec/req.agent.session)`；
- 拿不到（服务未挂载、会话未就绪）→ 退 `session.header.cwd`；
- 两者都拿不到，或拿到的不是绝对路径 → 返回 `null`，**只用全局规则**，并在 README 写清；
- 项目根只用来算项目标识（见 D-09），**配置本身不落在项目根**；
- **不**用 `process.cwd()` 冒充，**不**向上找 `.git`（多仓库、子模块、worktree 下会猜错；
  MVP 不需要）。

**被否方案**：

| 方案 | 为什么否 |
| :--- | :--- |
| `process.cwd()` | 与项目无关，最坏会把别的项目的规则套过来 |
| 向上找最近的 `.git` / `.svn` | 本机有聚合目录、多仓库、0 字节 `.git` 哨兵；猜错就是跨项目放行 |
| 取 `exec.arguments.workdir` | 只是单次命令的目录，不是项目根；很多命令不传 |
| 项目根算出来后再拼 `<项目根>/.dsh/...` 读配置 | 工作区可写，模型能自我放行；见 D-09 |

**复验**：`项目根退回 session.header.cwd；都拿不到时只用全局` 测试；真机取值列在 README
「已知限制 / 未验」。

## D-06 被否的总方案：拆复合命令、管 ssh_run、卡片实时交互（2026-11-01）

**拆复合命令**（按 `;` / `&&` / `|` / 换行切段逐条匹配）：

- 需要 shell 词法/语法（引号、转义、子 shell、PowerShell 与 bash 两套语法），写错一个引号就误判；
- 误判方向不可控：切错一段可能把危险命令当成安全段放过；
- MVP 的替代方案是「写整条正则」；用户明确说「按配置文件以正则匹配命令的一部分」，
  指的是用正则表达一条完整命令的形状，不是拆结构；
- 将来真要做，应作为独立决策重新评估。

**管 `ssh_run`**：那是 `dsh-ssh-remote` 自己的多选卡与执行协议，不经过
`approval/request`；把白名单伸进去等于在两个插件之间造隐式耦合。范围只做 pwsh/bash，
已在 BACKLOG 决策里由用户拍板。

**卡片实时交互**（审批卡上加「总是允许」）：用户明确说不做，名单由另一个会话维护配置文件。
加了会引出「卡片写配置的权限/格式/并发」一堆问题，且和「配置文件是唯一事实源」冲突。

**装 watcher（`fs.watch`）做热更**：编辑器保存常用「写临时文件再 rename」，不同平台/编辑器
事件形态不一；每次审批前 `stat` 一个 `allow.json` 是确定性的、成本可忽略（同步 stat 一次），
不需要处理 watcher 的生命周期与去抖。

**复用 `dsh-experimental-auto-review`**：那是「模型判断风险」，不是「用户名单」；且只在 Auto
preset 下工作。本插件要的是确定性的、用户可审计的规则。

## D-07 缓存 256 条 / 10 分钟，且不在审批后删除（2026-11-01）

**现象**：`tools/pre-execute` 与 `approval/request` 是两个事件，中间隔着 gate / guard / 沙箱
提权判断，必须用 `callId` 把命令带过去。

**根因**：没有命令文本的审批事件只能靠旁路缓存补上下文；缓存必须防泄漏、防无界增长。

**结论**：

- 上限 256、TTL 10 分钟，Map 插入序淘汰最旧；重复 `remember` 移到最新；
- 10 分钟覆盖「pre-execute 后等待审批 / 提权重试」的正常间隔；
- **审批后不删缓存**：同一个 `callId` 可能先触发一次普通审批（例如某个 guard 要求），
  再在 execute 内部触发提权审批；删了第二次就会缓存未命中而 fail-closed，违背「提权也归白名单管」；
- 缓存只存 `{tool, command}`，不存 agent / 会话，避免持有大对象。

**被否方案**：无界 Map（长会话泄漏）、审批后立即删除（破坏同 callId 的第二次审批）、
TTL 1 分钟（人工审批等待可能超过）、按命令哈希做 key（无法从审批事件推出哈希）。

**复验**：`缓存：默认 256 / 10 分钟…` 测试；真机提权审批列在 README「未验」。

## D-08 审计与诊断分开，写失败不影响审批（2026-11-01）

**现象**：审计是「另开会话统计近期审批」的数据源；配置错误是排查用的。两者混在一个文件里，
统计要过滤，排查要翻无关行。

**结论**：

- `<dataDir>/approvals.jsonl`：一行一条决策，六个键固定
  `ts / tool / command / outcome / rule / reason`，缺值 `null`，中文说明只放代码注释；
- `<dataDir>/config-errors.log`：配置诊断，一行一条 JSON；
- 两者都用 `appendFileSync`，`mkdirSync` 懒创建数据目录；任何写入异常 catch 住，
  首次失败打一条 `console.warn`（同一文件成功写入后重置），**绝不改变审批结果**；
- 审计只覆盖真正走到审批的 `pwsh` / `bash`，其他工具不记，避免噪音。

**被否方案**：写失败就拒绝审批（把可用性问题变成阻塞）、把审计塞进 session 日志（要懂 DSH
内部格式，且统计会话不好读）、只记 `auto-allowed` 不记 `asked`（统计不出「还在问什么」）。

**复验**：`审计字段稳定`、`审计写失败不影响放行` 两组测试。

## D-09 项目配置不放工作区：模型可写＝可自我放行（2026-11-01，B-43）

**现象**：最初把项目规则放在 `<项目根>/.dsh/approval-allow.json`。用户指出：工作区里的文件
模型自己能用 `write` / `edit` 写（不需要审批），等于让被审查方给自己发通行证。

**根因**：批准与否的规则如果放在被批准方有权写的地方，规则就不可信。普通
`workspace-write` 会话对工作区有写权限，对 `%USERPROFILE%\.dsh` 没有；沙箱边界才是唯一
可信的边界，目录约定不是。

**结论**：

- 唯一配置入口是 `<dataDir>/allow.json`；`dataDir` 默认
  `%USERPROFILE%\.dsh\plugin-data\approval-allow`（设 `DSH_HOME` 则在其下），在工作区外；
- 项目规则写在同一文件的 `projects.<项目标识>` 段，**不在项目目录落任何文件**；
- 项目标识 = `<slug>-<sha1(规范化小写绝对路径) 前 8 位>`：路径分隔符统一 `/`、去末尾 `/`、
  转小写，非 `[a-z0-9]` 连续段换 `-`、去首尾、最多 60 字符，空则 `root`。同一路径永远同一
  标识，不同路径靠 8 位哈希区分；项目根不是绝对路径时不生成标识，只用全局规则；
- 工作区里的 `<项目根>/.dsh/approval-allow.json` 和项目根 `allow.json` **一律不读、不 stat**，
  旧文件静默忽略（不产生诊断，避免每次审批都提旧路径）；
- `dataDir` 如果被配到工作区里，模型同样能写，安全边界失效；README 明确要求放在工作区外。
  若某次调用被提权到 `danger-full-access`，它理论上也能写 `dataDir`——边界仍是沙箱。

**被否方案**：

| 方案 | 为什么否 |
| :--- | :--- |
| 工作区 `.dsh/approval-allow.json` | 模型可写＝自我放行，正是本条要修的问题 |
| 项目根 `allow.json` / `.approval-allow.json` | 同上，只是换了个文件名 |
| 读项目文件里写的「配置路径」 | 路径仍来自工作区，可被模型伪造 |
| 用户手工给每个项目起名 | 要维护路径→名字映射，容易配错；路径算标识无状态、可复现 |
| 放 `%LOCALAPPDATA%` 等另起目录 | 与现有 `DSH_HOME/plugin-data` 约定分裂，多一套查找逻辑 |

**复验**：`项目标识…`、`项目配置只在 dataDir\allow.json；工作区里的 .dsh 与根 allow.json 都被忽略`、
`项目段并进同一个 allow.json…` 三组测试；本机 `dataDir` 默认路径见 README。

## D-10 一个插件一个目录、单一 allow.json，不建 projects 子目录（2026-11-01）

**现象**：项目规则最初按 `<dataDir>/projects/<标识>.json` 分文件。用户要求整理 `.dsh` 根：
最好只有一个我们的文件夹（`plugin-data`），里面按插件分；不要插件再建 `projects\` 这种
二级分类目录，也不要每个功能一个入口，否则看不出哪些是 DSH 自己的文件、哪些是插件的。

**根因**：`.dsh` 根下 DSH 自己的条目已经很多，插件再铺目录会让「谁的配置」不可读；配置入口
越分散，改错文件、看漏规则的概率越高。个人自用、单环境，不需要按项目/功能拆物理文件。

**结论**：

- `dataDir` 只允许三个文件：`allow.json`（唯一配置入口）、`approvals.jsonl`（流水）、
  `config-errors.log`（诊断，有错才出现）；**不建任何子目录**；
- 项目规则并入 `allow.json` 的 `projects` 段：`projects: { "<项目标识>": { deny, allow } }`；
- `projects` 是可选段；坏段/坏项按 D-04 局部忽略并写诊断，不拖垮顶层规则；
- 插件代码目录里的 `lib/`、`tests/`、`scripts/` 是源码结构，不是 `dataDir`，不适用
  「三文件」限制；生产树只按部署清单搬运行时代码。

**被否方案**：

| 方案 | 为什么否 |
| :--- | :--- |
| `projects/<标识>.json` | 多一层目录；看目录分不清是 DSH 还是插件的文件 |
| 每个项目一个 `allow-<标识>.json` 放 dataDir 根 | 入口分散，项目多了像垃圾场；还要动态发现文件 |
| 每个功能一个入口（`deny.json` / `allow.json` / `projects.json`） | 改一条规则要开多个文件，合并/优先级更难核 |
| 按环境/版本再分目录 | 个人自用单环境，纯增负担 |

**复验**：`项目段并进同一个 allow.json…` 测试断言 `readdirSync(dataDir)` 只有
`allow.json` / `approvals.jsonl`；坏 JSON 测试断言第三个文件只在出错时出现；README
「配置在哪」只有一张三个文件的表。

## D-11 维护会话的统计工具：只读、按前两个 token 归组、正则只泛化形状（2026-11-02）

**现象**：用户要另开一个会话专门看「最近哪些命令老是要问」，据此提白名单规则。流水
（`approvals.jsonl`）是原始行，直接看只能看到一堆脚本头和重复命令，看不出「该给哪条命令写规则」。
工具是 `tools/approvals-report.ps1`，默认零参数出一份 Markdown 报告。

**根因**：流水回答的是「这次问了什么」，规则需要的是「**命令族**长什么样」。中间要补三件事：
把多行脚本压成一行、把同一族的写法聚成一组、把一组命令的「形状」写成一条能直接粘进 `allow.json`
的全锚定正则。这三件事都是**判断**，所以工具只摆在维护会话手边，不塞进插件运行路径。

**结论**：

- **只读，绝不写 `allow.json`**：插件自己都不写配置（D-06「卡片实时交互」被否），统计脚本更不能——
  它读的是命令原文，一旦能写配置就等于「模型能给自己放行」（B-43 / D-09）。脚本不碰 `dataDir`
  里除 `approvals.jsonl` 之外的任何文件，改名单由人和会话决定；写宽了等于把审批关掉。
- **放 `tools/` 而不是 `dsh-approval-allow/scripts/`**：它是维护侧工具，不进插件运行时；生产树只按
  部署清单搬运行时代码，所以它不会上线、也不该被插件 `require`。
- **归组两级**：第一行 → 首 token 作「命令族」（报告顶部给一行汇总），**前两个 token 作表行**
  （`git fetch`、`git commit`）。理由：写规则时人按子命令写（`^git fetch …$`），按一个 token
  太粗（`git` 一条规则等于放开所有 git），按整条命令太细（`git fetch --all` 与 `git fetch origin`
  会拆成两行）。同一组的多种写法仍能看出来：样例列给组内**出现最多**的具体写法，其余写法在风险列
  写「另有 N 种写法（此正则只覆盖样例）」——因为一条正则只覆盖样例那一种，不提示就会被漏掉。
  多行命令只取第一行（流水里的 `command` 是整段脚本），风险列同时标「多行，不能单条锚定」。
- **正则只泛化形状、不猜语义**：`'…'`→`'[^']*'`、`"…"`→`"[^"]*"`、独立数字→`[0-9]+`、
  含 `/` 或 `\` 的 token→`[A-Za-z0-9._\\/:-]+`，其余原样转义。不做「同类命令合并成 `(a|b)`」、
  不把 `--force` 之类危险参数泛化掉：规则的责任在人，脚本只把重复劳动省掉。
  字符类里多带一个 `:`（相对 D-11 举例的 `[A-Za-z0-9._\\/-]+`）是为了 Windows 盘符路径也能匹配；
  能替换的前提是**这个 token 的每个字符都在类里**，否则退回字面——不匹配的 token 宁可不泛化。
- **自检与插件同口径**：生成后用 .NET 正则按插件同样的判定（`index = 0` 且命中长度等于命令全长）验一遍，
  不过就在风险列写「生成失败，人工写」。没有样例（`command` 为 null）时不报生成失败，直接给 `-`。
  额外用 Node 把生成的正则跑了一遍 `new RegExp` + 全文匹配（插件是 JS 正则），8 条全部通过。
- **正则从完整第一行生成，样例才截断到 60 字符**（按字符不是字节）：从截断后的字符串生成会把规则
  写残；样例只是给人看的。
- **竖线写成 `\x7C`**：Markdown 表格里 `\|` 的反斜杠会被吃掉，粘回 `allow.json` 就变成「或」；
  `\x7C` 在 .NET 与 JS 正则里都是同一个字面竖线，也不再需要表格转义。
- **风险列看整条命令原文**（含多行）：`rm -rf`、`sudo`、`--force`、`git reset --hard`、
  `curl … | sh`、`> /dev/sd`、`rmdir /s`、`format`、`DROP TABLE`、`drop database`、`truncate`、
  `shutdown` 这些宁可多标。副作用是「写 allow.json 的脚本里嵌了 `--force` 字样」也会被标——
  这种脚本本来就该人工写规则，多标不吃亏。
- **分节不重复计数**：默认主表只放 `asked + no-rule`；`-IncludeDeny` 把 `deny-rule` 放单独一节；
  `-All` 再加一节「自动放行 / 其它原因」。每条流水只出现在一节里，避免同一行被算两次。
- **fail-closed 的读法**：文件不存在 → 「还没有流水：<路径>」+ 退出码 0（没流水不是错误）；
  坏行（坏 JSON / 顶层不是对象 / `ts` 解析不出）跳过并计数，末尾报「跳过坏行 N 行」；空行不算坏行。
  没时间戳的行进不了「近期」统计，所以按坏行算，但单独计数（`ts 无法解析`）。

**被否方案**：

| 方案 | 为什么否 |
| :--- | :--- |
| 按整条命令（第一行）归组 | `git fetch --all` / `git fetch origin` / `git fetch --prune` 会各占一行，人得自己看出它们是一族 |
| 按单个首 token 归组 | `git` 一条规则等于放开整个 git，和「不写 `^git .*$`」的纪律冲突 |
| 只按归一化后的命令（替换掉可变部分）分组 | 归一化本身有猜测成本；同样的命令换个参数顺序就被拆开，人反而看不出「它在问什么」 |
| 脚本自动把选中的规则写进 `allow.json` | 决定放行的配置不能在模型可写的地方被模型写（D-09）；且「哪些该放行」是人的判断 |
| 用 `.*` 兜住命令尾部（`^git fetch .*$`） | 等于放过 `git fetch && rm -rf`；插件只认整条锚定，照顾不了复合命令 |
| 在报告里给每条命令直接生成多个备选正则 | 多行候选会让人挑花眼，也把「选规则」的责任从人身上挪走 |

**复验**（都跑过）：

- 真实流水：`pwsh -NoProfile -File tools\approvals-report.ps1`（默认口径 5 行 / 4 组，坏行 0）；
  `-IncludeDeny` 多出 `git push --force` 一节（风险列 `--force / push -f（强推）`）。
- 假流水（`.tmp/fixture.jsonl`，跑完即删）：多行命令→标「多行」且正则取第一行；坏 JSON 1 行 +
  坏 `ts` 1 行 → 「跳过坏行 2 行」；`reason=deny-rule` 只在 `-IncludeDeny` 的节里；`command=null`
  → `(无命令)` 组（风险 `-`，不出正则）；`git fetch --all` ×3 + `origin` + `--prune` → 一组 5 次、
  样例取 `--all`、风险提示「另有 2 种写法」；`-Top 3` 打印「只列前 3 组，共 8 组」；
  `-Since` 只剩 11-01 10:04 之后的 7 行；空文件/全坏文件 → 0 行 + 「跳过坏行 N 行」；传目录 →
  「还没有流水：…」。
- JS 口径：把报告里的 8 条正则交给 Node `new RegExp` + 全文匹配，全部可编译且各命中自己的样例。
- 一个坑写在这里：PowerShell 绑定 `[Nullable[datetime]]` 参数时会把值**退化成 `[datetime]`**，
  判空只能看 `$null`，`.HasValue` 会抛「property cannot be found」（`-Since` 首次实现就踩了）。
